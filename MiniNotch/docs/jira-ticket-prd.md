# PRD：Jira Ticket 订阅与事件中心

> 版本 v0.1 · 基于 [today-analysis.md](today-analysis.md) 第 3.1/3.3 节及改进清单 #1/#2/#4/#5/#6。
> 配套技术设计参照 [AI_UPGRADE_DESIGN.md](AI_UPGRADE_DESIGN.md) 的共享基建（IndexedContext / ProactiveGate）。

---

## 1. 背景与问题

### 1.1 现状

当前 Jira 集成是一条写死的 `assignee = me` 轮询（JiraService），结果全部压成 `Todo` 进入
统一待办列表，只读镜像，仅在**新指派**时弹通知卡，状态变化静默覆写（AppStore.swift `mergeExternalTodos`）。

### 1.2 问题（来自五角色分析）

| # | 问题 | 受害角色 |
|---|---|---|
| P1 | 状态流转不通知——QA 等的"已修复待验证"、BA 等的"Story 被打回"恰好是唯一不通知的事件 | QA / BA / PM / TL |
| P2 | `assignee = me` 对 BA（reporter 视角）、PM（sprint 全景）、TL（监督视角）是接近空集的查询 | BA / PM / TL |
| P3 | 所有票一律渲染成待办行——PM 关心三个 sprint 百张票但绝不要一百行待办；TL 的监督票淹没自己的任务 | PM / TL |
| P4 | 只读镜像 = 能看的徽章：改状态/评论仍要开浏览器，最高频动作参与度为零 | 开发 / QA / TL |
| P5 | 关联票（前后端/父子）完全不可见，开发和 QA 缺上下文 | 开发 / QA |

### 1.3 核心判断

**五个角色对 Jira 的关注差异不是矛盾，是三个正交变量的不同取值：查询范围（JQL）、
渲染形态、触发事件。** 解法不是五套角色模式，而是把这三个变量交还给"订阅"配置，
辅以角色预设包降低配置成本，用 AI（自然语言→订阅）兜住个性化长尾。

## 2. 目标与非目标

### 目标

1. 任一角色装上产品 3 分钟内能看到**对自己有意义**的 Jira 数据（角色预设一键装载）
2. 用户关心的**状态事件**主动找到用户（弹卡），而不是用户轮询 Jira
3. 高频写操作（状态流转）**不离开刘海**完成
4. 全程守住两条语义红线：
   - "今日可动手数"只含我可执行的事（aggregate/eventOnly 的票绝不污染计数）
   - 打扰预算全局治理（接入 ProactiveGate，事件卡服从全局限频）

### 非目标（本期不做）

- Jira 评论流/工时登记（写回只做状态流转）
- 跨项目报表、燃尽图表绘制（aggregate 只做计数与信号灯，不画图）
- Jira 之外数据源的 Lens 化（GitHub 沿用现状，架构预留）
- 关联票的递归图谱（只展示一度关联）

## 3. 核心概念与信息架构

### 3.1 订阅（Lens）

用户持有若干条订阅，每条 = 查什么 + 怎么显示 + 什么事件叫我：

```
JiraLens
├─ name        订阅名（"待我验证" / "本 sprint 全景"）
├─ jql         JQL，支持模板变量 {me} {project} {sprint}
├─ display     渲染原语（三选一，见 3.2）
└─ notifyOn[]  触发规则：newTicket / statusChange(to:) / statusChange(any)
               / staleDays(n) / dueSoon / reopened
```

### 3.2 三种渲染原语（本 PRD 的基石约束）

| 原语 | 去向 | 参与今日计数/提醒 | 适用 |
|---|---|---|---|
| `todoRows` | Today/Inbox 任务行 | ✅ | 我可执行的票（我的开发票、待我验证的 bug、待我 review） |
| `aggregate` | 面板聚合行 + compact 信号 | ❌ | 监督/进度对象（组内票、我提的 Story、sprint 全景） |
| `eventOnly` | 平时不可见，事件命中弹卡 | ❌ | 纯哨兵（"高优 bug 空降"、"我提的票被打回"） |

### 3.3 角色预设包（出厂配置）

| 预设 | 内含订阅（display / notifyOn） |
|---|---|
| 开发 | ① 我的开发票 `assignee={me} AND type in (Task,Bug) AND sprint in openSprints()` → todoRows / newTicket+reopened |
| 测试 | ① 待我验证 `status="待验证" AND assignee={me}` → todoRows / statusChange(to:待验证)<br>② 我提的被重开 `reporter={me} AND status=Reopened` → eventOnly / reopened |
| 需求分析 | ① 我提的 Story `reporter={me} AND type=Story` → aggregate(按 epic) / statusChange(any) |
| 技术 Leader | ① 待我 Review → todoRows / newTicket<br>② 组内开发票 `project={project} AND sprint in openSprints()` → aggregate / staleDays(3) |
| 项目经理 | ① 三 sprint 全景 `sprint in ({prev},{current},{next})` → aggregate / staleDays(3)+newTicket(高优) |

规则：预设是**起点不是模式**——装载后可自由增删改单条订阅；多预设可叠加（TL 同时装开发包）。

## 4. 功能需求

### F-J1 多订阅轮询引擎 — P0

| 需求项 | 说明 |
|---|---|
| JT-101 | JiraService 支持 N 条 Lens 轮询，共享现有 Timer（`jiraPollSeconds`），多条 JQL 错峰串行发起 |
| JT-102 | `mergeExternalTodos` 合并/镜像清理维度从 source 细化到 lens id；仅 `todoRows` 类订阅走此管线 |
| JT-103 | `aggregate` 类结果不进 todos，单独发布 `jiraAggregates`（与 meetings 平级的数据流） |
| JT-104 | JQL 模板变量 `{me}/{project}/{sprint}` 在请求前解析；解析失败的订阅标记错误态，不阻塞其他订阅 |
| JT-105 | 同一张票命中多条订阅时去重：todoRows > aggregate > eventOnly，取最高优先的渲染，事件订阅照常触发 |

**验收**：配置 3 条不同 display 的订阅，todos 列表只出现 todoRows 的票；关掉某条订阅，其镜像票在下个轮询周期被清理且不误删其他订阅的票。

### F-J2 状态事件检测与通知卡 — P0

| 需求项 | 说明 |
|---|---|
| JT-201 | 轮询 merge 时 diff 新旧 `jiraStatus/jiraStatusCategory`，按订阅的 notifyOn 规则产生事件 |
| JT-202 | 事件卡新增 IslandState case `.jiraEvent(event, moreCount)`，几何同现有 jiraLanded（380pt 卡） |
| JT-203 | 事件经 ProactiveGate：勿扰时段不弹、岛非 compact 不弹、全局限频；被压制的事件落入面板"事件流"区静默标记 |
| JT-204 | 同轮多事件合并为一张卡 + "等 N 条"（沿用 jiraLanded 的 moreCount 模式） |

**验收**：测试预设下，把一张 bug 在 Jira 改为"待验证"，下个轮询周期内弹出事件卡；同一张票不重复弹；勿扰时段改状态，事件出现在面板事件流而非弹卡。

**Prompt 草案（jsonMode）**：

```
你是 Jira 查询助手。把用户的一句话需求转换成一条订阅配置。
只输出 JSON：{"name": "≤8字", "jql": "...", "display": "todoRows|aggregate|eventOnly",
"notifyOn": ["newTicket"|"statusChange:状态名"|"staleDays:3"|"reopened"|"dueSoon"]}
可用项目：{projects}；可用状态：{statuses}；可用类型：{types}；当前用户：{me}。
规则：
- jql 中的项目/状态/类型只能取上述枚举值，人名用 {me} 或站点真实账号
- display 判断：用户要"自己处理的事"→todoRows；要"看进度/全景"→aggregate；要"出事叫我"→eventOnly
- 拿不准时 display 取保守值（aggregate），notifyOn 宁缺勿滥
```

## 6. 数据与接口变更

| 变更 | 内容 | 契约影响 |
|---|---|---|
| 新模型 `JiraLens` | 见 3.1，持久化进 settings.json（向后兼容解码） | AppSettings 加字段，按惯例补 decodeIfPresent |
| 新模型 `JiraAggregate` | `{lensName, groups: [{key, counts}], health}` | 新增，不动 Todo |
| 新模型 `JiraEvent` | `{ticket, kind(new/transition/stale/reopened), from, to, at}` | 新增 |
| `Todo.lensID: UUID?` | 镜像清理与去重的归属维度 | **改 Models.swift，需开 openspec change 通知全员** |
| IslandState | 新增 `.jiraEvent(event:moreCount:)`；`jiraLanded` 收编为其特例（kind=new） | 状态机扩展，几何复用 |
| JiraService | 多 Lens 轮询、transitions 拉取与执行、issuelinks 按需拉取、JiraMeta（项目/状态/类型枚举）缓存 | 协议扩展 |
| AIService | 新增 `generateLens(text:context:)` | 协议扩展，Mock 返回固定 Lens |

API 速率评估：每用户订阅数预期 2~5 条，60s 轮询周期内串行 5 个 JQL search 请求，
远低于 Atlassian Cloud 限流阈值；transitions/issuelinks 均为用户动作触发的按需请求。

## 7. 打扰预算与红线（继承全局规则）

1. 事件卡走 ProactiveGate：任意两张主动卡间隔 ≥10 分钟，用户截止提醒永远优先
2. 被压制/合并的事件**绝不丢**，落入面板事件流（5.3）——"错过弹卡"不等于"错过事件"
3. aggregate/eventOnly 的票永不进入 `todayActionableCount`、永不触发四级到期提醒
4. compact 健康灯至多 1 枚（JT-703）
5. 监控类提示的措辞红线：面向"事被卡住"，不面向"人没干活"——"MD-1024 停在张三处 4 天，问问？"
   可以；任何绩效化、排名化表述不可以

## 8. 度量（设计自检用，hackathon 不埋点）

| 功能 | 北极星 | 反指标 |
|---|---|---|
| 事件卡 | 卡上动作点击率；"流转→响应"时长缩短 | 秒关率 >50%（预算透支） |
| 写回 | 岛上完成的流转次数 / 跳 Jira 次数比值上升 | 写回失败率（工作流配置不兼容信号） |
| Lens | 非开发角色的订阅留存（装了预设没关掉） | 单用户订阅数 >8（配置失控信号） |
| NL 生成 | 生成→保存转化率 | dry-run 命中 0 票的比例（生成质量差） |

## 9. 里程碑

| 阶段 | 范围 | 演示价值 |
|---|---|---|
| M1（P0） | F-J1 多订阅引擎 + F-J2 状态事件卡 | QA 故事线成立："改状态→刘海弹卡" |
| M2（P1） | F-J3 写回 + F-J4 预设/管理页 | 闭环成立："弹卡→岛上验证通过→Jira 变化" |
| M3（P1） | F-J5 NL→订阅 | AI 高潮："一句话生成一条订阅，dry-run 命中 4 张票" |
| M4（P2） | F-J6 详情关联 + F-J7 compact 信号灯 | PM/TL 叙事补全 |

依赖关系：M2 依赖 M1 的 Lens 模型；M3 依赖 M2 的订阅管理页承载确认卡；M4 独立可并行。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 各站点 Jira 工作流差异大，写死状态名必翻车 | JT-301 动作集从 transitions API 实时拉取；预设包中的状态名装载时与 JiraMeta 校验，不匹配则提示用户修正 |
| 订阅配置复杂度劝退非技术角色 | 三道防线：零配置默认开发预设 → 预设包覆盖 80% → NL 生成兜底；裸 JQL 永远折叠在"高级" |
| LLM 生成的 JQL 不可靠 | dry-run 强制试运行 + 命中数回显 + 语法错自动修复 ≤2 轮 + 人工确认卡（JT-502/503） |
| 多订阅去重/镜像清理出 bug 导致数据丢失 | JT-105 优先级规则单元测试覆盖；镜像清理仅作用于 lensID 归属的票（沿用 prune 的来源隔离思路） |
| 事件风暴（sprint 切换时批量流转） | JT-204 同轮合并 + ProactiveGate 限频 + 事件流兜底 |
