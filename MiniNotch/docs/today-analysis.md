# MiniNotch 产品分析：角色价值、鸡肋点与改进方向

> 汇总自五轮产品讨论：开发人员 / 测试人员 / 需求分析人员 / 项目经理四个角色的
> 价值-鸡肋-建议分析，加上"五角色 Jira 视角冲突"的架构方案，并补充若干新思考。
> 配套的 AI 功能细化设计见 [AI_UPGRADE_DESIGN.md](AI_UPGRADE_DESIGN.md)。

---

## 〇、产品现状一句话

MiniNotch 当前是一个 **me-centric 的个人待办聚合器**：零摩擦录入（⌘N / 截图 AI 解析）+
外部源只读镜像（Jira `assignee=me`、GitHub PR、日历）+ 四级到期提醒 + AI 晨晚报，
以 macOS 刘海为统一的注意力出口。

**站得住的灵魂是两点：零摩擦录入 + 余光里的安心。**
最大的风险是被做成"更漂亮的只读看板 + 会写作文的 AI"——看板因只读而鸡肋，作文因没有去处而被跳过。

## 一、各角色的工作本质（决定一切结论的前提）

| 角色 | 工作本质 | 节奏特征 | 任务对他是什么 |
|---|---|---|---|
| 开发 | 产出代码 | **flow 驱动**：少量大块任务，怕被打断 | 自己执行的事 |
| 测试 | 产出验证结论 | **事件驱动**：大量小块任务，等别人的动作触发 | 等外部事件解锁的事 |
| 需求分析 | 产出共识 | **会议驱动**：捞需求、对齐、分发、追闭环 | 大部分是**别人做的事** |
| 项目经理 | 产出"按时交付" | **全局监控**：发现偏差、协调、汇报 | 所有人任务总和的**健康度** |
| 技术 Leader | 产出技术决策与团队产出 | **混合**：自己写码 + Review 把关 + 监督进度 | 任务 + 监督对象的混合体 |

> 一条贯穿全文的判断：产品当前按开发者的节奏长出来，离"我的待办"越远的角色，
> 现有功能命中率越低——PM 是错位最深的角色（坐在驾驶位，仪表盘显示的却是乘客的待办清单）。

## 二、分角色：真实帮助与鸡肋点

### 2.1 开发人员

**真实帮助**
- **录入零摩擦**是最扎实的价值：⌘N 一句话 + AI 解析，全程不离开当前窗口，解决"记一条任务要切走"导致的 flow 中断。刘海形态在此加分：永远在屏幕顶端，无窗口管理。
- **"别人欠我的/我欠别人的"聚合一瞥**：Jira 指派 + GitHub 待 review + 下个会议，替代"轮询三个网站"的碎片注意力。PR review 是团队最经典的掉球点，常驻可见有真实协作价值。
- **安静的紧急度信号**：compact 颜色分级（normal→near 弱脉冲→urgent 闪烁）是 calm technology 的正确做法，绕开"通知太多导致全部免疫"的问题。

**鸡肋点**
- **Jira/GitHub 只读镜像 = 能看的徽章**：看到 ticket 后改状态/评论/登工时仍要开浏览器，实际角色退化为"另一个会稍微过期的列表"。最大的半成品感来源。
- **晨晚报演示惊艳、日常跳过**：LLM 长文塞 460×540 面板，信息密度低、内容是已知事实的复述；固定 18 点弹晚报有打扰嫌疑。生成式"报告"是 hackathon 经典陷阱。
- **截图解析对开发是低频**：开发的任务来源是文字/链接/通知，截图是绕路（注：对 QA 恰恰相反，见 2.2）。
- **个人 Todo 与 Jira 双轨制**埋着"记账分裂"的雷：用户开始想"这条该记哪"的那一刻就开始流失。
- **刘海本身有一部分是噱头**：compact 态只能承载一个数字加倒计时，大部分功能活在展开面板里——面板形态与菜单栏应用无异。可持续价值在聚合+录入引擎，刘海只是讨喜的展示位，别把工程预算持续投在"再炫一点"上。
- **固定文案的 AI 建议条**信息量等同星座运势，三天内被眼睛自动跳过。

### 2.2 测试人员

**真实帮助**
- **截图解析链路对 QA 是真命中**（比开发高一个量级）：QA 的任务输入天然是截图——群里的崩溃截图、用户反馈截图。"截图→结构化待办"正中其任务摄入流。现有功能里最被低估的 QA 资产。
- **碎片化多任务的计数节奏**：QA 一天是几十件 15 分钟级小事，刘海计数器对"任务多到记不住"的形态匹配度高于开发。
- **截止紧急度踩中发版节奏**："18:00 提测截止"是硬 deadline，urgent 态对此提示价值实在。

**鸡肋点**
- **通知触发事件押错了（最致命）**：`mergeExternalTodos` 只在**新指派**时弹卡，状态变化静默更新。但 QA 的核心触发事件是**bug 流转到"已修复待验证"的那一刻**——产品对 QA 的核心节拍失聪。
- **只读对 QA 比对开发更痛**：QA 的核心循环本身就是写操作（验证通过→关闭 / 不通过→重开+评论），这个循环在岛上参与度为零。
- **GitHub PR 模块对多数 QA 是空集**。
- **AI 解析缺 QA 关键维度**：环境与版本（"staging 上验 v2.3.1"）无法结构化。
- **晚报多一层讽刺**：QA 是被要日报最多的角色，晚报给的却是没法交差的散文。

### 2.3 需求分析人员（BA）

**真实帮助**
- **批量解析会议纪要是为 BA 量身定做的**——Mock 数据（"陈昊跟进 API 文档…"）本身就是一份带别人名字的 BA 会后行动项清单，产品无意识地演示了 BA 场景。会议纪要截图→行动项草稿→勾选确认，对 BA 是散会后每天都做的核心动作。
- **会议侍从价值高**：BA 会议密度高，倒计时/平台标识/一键入会是高频减负。
- **碎片承诺捕捉**："回头发你竞品分析"类口头承诺无系统承载，⌘N 正中。

**鸡肋点**
- **根本性模型错位**：解析出"陈昊跟进 API 文档"，落库后变成"我"的待办——`Todo` 无 assignee 概念，到期时我的任务其实是**催陈昊**，提醒对象/动作/话术全错。把"委派-跟催"语义压扁成"自己的待办"，等于用单人游戏的存档格式存了一局多人游戏。
- **没有"等待中"状态**：BA 一半任务在等人（"等客户确认"），不该计入"今日可动手数"，需要的是老化提示（"等了 3 天"）。snooze 是"我晚点做"，不是"我在等谁"。
- **Jira 集成对 BA 是空集**：他关心"我提的需求们走到哪了"（reporter 视角的全景），不是"指派给我的票"。
- **任务缺"所属需求/项目"维度**：BA 的行动项天然按需求聚类，现在全部平铺等于把文件柜倒在桌上。

### 2.4 项目经理（PM）

**真实帮助**
- **会议侍从价值在 PM 达到峰值**：背靠背的会是常态，urgent 态对 PM 的实际含义基本是"该进会议室了"。
- **协调类承诺捕捉**："我去协调测试资源"类口头领走的事无系统承载。
- 诚实地说，**到此为止**——现有功能对 PM 的命中只有这两条通用价值。

**鸡肋点**
- **`assignee=me` 对 PM 是接近空集的查询**：PM 几乎不被指派开发工单，打开产品看到一片空白。他要的是 sprint 全景：燃尽偏差、谁过载、哪张票滞留。
- **提醒模型不懂"关键路径"**：普通任务超期一天无关痛痒，关键路径超期一小时就是项目延期信号；里程碑前三天就该黄灯。时间临近度 ≠ 项目风险度，现有模型只有前者。
- **个人清零庆祝是反讽**：PM 待办清零戴皇冠的那天，项目可能正在着火——精准暴露 me-centric 模型错位。
- **晨晚报第四次落空且受害最深**：PM 写报告耗时最长，要的是数字（完成率/燃尽偏差）和风险清单。

### 2.5 技术 Leader（补充分析）

> 前四轮未单独分析，从 Jira 视角讨论中补全。

TL 是**混合体**：自己有开发票（同开发人员的全部价值与痛点），同时承担 Review 把关与团队监督。

- **Review 票是他真正的待办**，且是全团队流速的咽喉——TL 的 review 延迟一天，N 个开发阻塞一天。现有 GitHub PR 集成对 TL 价值最高，但"PR 等了多久、diff 多大、CI 过没过"这些决定"现在 review 还是晚点 review"的信息全缺。
- **组内开发票是监督对象不是待办**：他需要的是 aggregate（组内进度一览）+ 异常事件（某票滞留 3 天），灌进自己的待办列表只会淹没真正要做的事。
- **独有鸡肋**：产品完全没有"团队"概念，TL 的"我的事"和"我盯的事"在数据模型里无法区分——这与 BA 的"我做的 vs 我催的"是同一个缺口的两种表现。

## 三、跨角色汇聚：四条主干结论

五轮分析的结论高度收敛，这通常说明它们是产品的正确主干，而非某个角色的定制需求。

### 3.1 任务数据必须和外部世界双向流动

四个角色从不同痛点指向同一句话：

| 角色 | 诉求 | 本质 |
|---|---|---|
| 开发 | **写回**（一键 In Progress / Done / Approve） | 数据流出去 |
| 测试 | **状态事件**（"待验证"流转通知） | 事件流进来 |
| BA | **跟催闭环**（委派、老化、催办话术） | 对他人行动的流动 |
| PM | **偏差雷达**（滞留/过载/空降异常） | 对全局偏差的流动 |

只读镜像 + 死数据待办，是所有角色鸡肋感的共同根源。

### 3.2 报告的正确形态 = 同一套数据 × 角色模板 × 一键去处

晨晚报连续四轮落空，但每个角色都有真实存在、真实厌恶的"交差"场景：

- 开发 → **站会助手**：昨天做了 X（完成 todo + merged PR），今天 Y，阻塞 Z，一键复制 Slack
- 测试 → **测试日报**：执行 X 项验证、新发现 N 个 bug、阻塞项
- BA → **需求速报**：今日推进/阻塞/明日关键
- PM → **一页纸项目状态**：燃尽偏差、风险清单、下周关键路径

共同点：AI 产出第一次有了**去处**，而不是看完即焚的自我感动文。成本主要是 prompt 模板 + 复制按钮。

### 3.3 Jira 多视角不是矛盾，是"订阅 Lens + 三种渲染原语"

五个角色对 Jira 的关注差异，拆开只有三个正交变量：**JQL 范围、渲染形态、触发事件**。
解法不是五套角色模式，而是：

```
JiraLens = { name, jql(模板变量 {me}/{project}/{sprint}), display, notifyOn[] }

display 三种渲染原语：
  todoRows   — 进 Today/Inbox，参与计数和提醒（仅限"我可执行"的票）
  aggregate  — 只出聚合行/信号灯（"开发中 5 / 待测 3"），票不进列表
  eventOnly  — 平时不可见，事件命中时弹卡
```

- **角色预设 = 订阅组合包**而非模式开关——真实的人是混合角色（TL 同时是开发），角色锁死必然有人不适配，订阅组合永远适配。
- **关键约束**：PM 关心三个 sprint 一百张票，但绝不想要一百行待办。"关心 ≠ 变成待办行"——这是现在五个角色互相打架的真正原因，也是 `todayActionableCount` 语义纯洁性的守护线。
- **关联票（前后端/父子）不进订阅**：在详情页按需拉 `issuelinks`/`parent` 展示局部关系图，上下文不是列表项，更不该轮询。
- 落地成本低：多条 JQL 共享现有轮询 Timer；`mergeExternalTodos` 的合并/镜像清理把维度从 source 细化到 lens id；状态 diff 一处实现服务所有角色。
- **AI 的正确位置：自然语言 → 订阅**。JQL 对 BA/PM/QA 是天书，"我想盯着支付改版流转到待验证的 bug"→ LLM 生成 JQL + 触发规则 + 渲染建议 → 用户确认。延续"AI 草拟、人确认"哲学，把五种视角从产品要预判的难题变成用户一句话的自助能力。

### 3.4 产品的正确抽象

> **统一的注意力出口（刘海）× 可订阅的事件源（按角色）× 可切换的报告模板（按角色）**

这三件事比任何单点 AI 功能都更值得占用剩余的开发时间。

## 四、补充思考（讨论中未充分展开的）

### 4.1 战略定位的岔路口：个人效率工具，还是团队工作流入口？

当前产品站在岔路口上：

- **个人效率工具**路线：竞品是 Things/Reminders/Raycast，护城河只有刘海形态——很薄，菜单栏应用一周能抄走。
- **团队工作流入口**路线：竞品变成"打开浏览器"这个习惯本身。订阅 Lens、写回、跟催、角色模板都在这条线上。它的护城河是**对组织内工作流的理解深度**（哪些状态流转值得通知、哪种催办话术得体），这是抄不走的。

五轮分析实际上一直在把产品往第二条路推。如果团队认同，应该明确说出来，让它指导每一次功能取舍。

### 4.2 打扰预算是产品唯一真正稀缺的资源

刘海的全部价值建立在"用户允许它出现在余光里"之上。每一个新功能都在消费同一份预算：
nudge、跟进卡、Jira 落地、状态流转、异常雷达、四级提醒……**单看每个都合理，叠加起来就是把用户训练成无视刘海**——那一刻产品死亡。

治理必须全局而非各自为政（AI_UPGRADE_DESIGN.md 的 ProactiveGate 是雏形）：
- 主动卡全局限频（任意两张间隔 ≥10 分钟），用户主动设的截止提醒永远优先
- 打扰分级预算：每天主动弹卡总数有上限，超出的降级为面板内静默标记
- **反向思路是差异化机会**：刘海知道用户的全部上下文，因此知道**什么时候不该打扰**。
  Focus 模式（检测投屏/全屏 IDE 时积压非紧急通知，出 focus 后一张卡汇总）——
  市面上做"更响的提醒"的产品无数，做"更聪明的安静"的几乎没有。

### 4.3 隐私与信任边界

往团队路线走必然触碰敏感数据，提前画线比出事后补救便宜：
- **截图解析**把屏幕内容（可能含客户数据、密钥、聊天隐私）发给云端 LLM——需要发送前预览确认 + 明确的"哪些内容会上传"说明；长期可考虑本地模型兜底。
- **跟催/异常雷达**本质是对同事行为的监控（"陈昊的票停了 4 天"）。措辞决定产品气质：给用户的提示是"可能卡住了，问问？"而不是绩效语言。这条线一旦越界，产品在团队里会从受欢迎变成被抵制。
- 公司 Jira/GitHub 数据喂给 LLM 生成报告，需要确认组织的合规口径（hackathon 可豁免，产品化不能）。

### 4.4 价值如何验证：给每条主干配一个可观测指标

| 主干 | 北极星指标 | 反指标（警惕） |
|---|---|---|
| 零摩擦录入 | 周人均 ⌘N/截图录入次数 | 录入后 7 天未完成也未处置的比例（堆积 = 假录入） |
| 余光安心 | compact 态 hover/展开频率**下降**（瞟一眼就够 = 成功） | 主动卡的秒关率（>50% = 打扰预算透支） |
| 状态事件 | 事件卡点击率、"待验证→验证完成"的响应时长缩短 | 事件卡被静默忽略率 |
| 角色报告 | "一键复制"使用率（有去处的硬证据） | 报告生成后未复制率 |

hackathon 当然不做埋点，但**用这套指标反推设计**很有用：例如"晨晚报"若预期复制率低，就不值得做长文渲染。

### 4.5 配置复杂度是订阅模型的暗礁

Lens 模型的能力上限高，但配置界面做复杂了会劝退所有非技术角色。守住三道防线：
1. 默认体验零配置（装上就是开发预设，因为首批用户是你们自己）
2. 角色预设一键装载，覆盖 80% 的人
3. NL→JQL 兜住剩下 20% 的个性化——**绝不暴露裸 JQL 编辑器作为主路径**

### 4.6 对 hackathon 叙事的建议

评委叙事和产品真相可以是同一个故事的两个剖面：
- **演示线**（5 分钟）：一个开发者的一天——截图落任务（已有，稳）→ 状态流转弹卡"可以验证了"（新，命中事件主干）→ 站会前一键复制晨报（新，命中去处主干）→ NL 生成一条订阅（新，AI 高潮）。
- **愿景线**（1 页）：五角色 × 订阅 × 模板的矩阵图，讲"一个刘海，每个角色都离不开"。
- 砍掉的勇气：晨晚报长文渲染、更多庆祝动效、截图解析的边角 case 打磨——它们不在任何主干上。

## 五、改进点总清单（按价值/成本排序）

| # | 改进点 | 受益角色 | 成本 | 依赖 |
|---|---|---|---|---|
| 1 | 状态流转事件检测（merge 时 diff 新旧状态，弹卡） | QA/BA/PM/TL | 小 | 无 |
| 2 | Jira/GitHub 写回（状态流转一键化，先做 In Progress/Done/验证通过） | 开发/QA/TL | 中 | 无 |
| 3 | 报告角色模板 + 一键复制（站会/测试日报/需求速报/项目状态） | 全角色 | 小 | 无 |

## 六、一段话总结

MiniNotch 的灵魂——零摩擦录入与余光里的安心——在四个角色身上都得到了验证，但产品当前的
me-centric 只读模型让价值随角色离"自己的待办"越远衰减越快：开发觉得镜像鸡肋、测试觉得它失聪、
BA 觉得它拿错了说明书、PM 觉得仪表盘装错了。五轮分析收敛出的答案不是五套角色定制，而是一次
抽象升级：**让任务与外部世界双向流动（写回 + 事件），让关注成为可订阅的参数（Lens × 三种渲染），
让 AI 产出有去处（角色模板 × 一键复制），并把打扰预算当作产品最稀缺的资源来治理。**
刘海是这一切的注意力出口，而不是产品本身。
